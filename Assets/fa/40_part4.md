# 22. سیستم‌های کاربردی

بلوک‌های ساختمانی کوچک و قابل‌اعتمادی که تقریباً در هر بازی‌ای پیدا می‌شوند. خودت تایپشان کن، منطق هر تصمیم را بفهم، بعد تطبیقشان بده با بازی خودت.

## 22.1 قرارداد آسیب و Health

```csharp
public readonly struct DamageInfo
{
    public readonly int Amount;
    public readonly Vector3 HitPoint;

    public DamageInfo(int amount, Vector3 hitPoint)
    {
        Amount = amount;
        HitPoint = hitPoint;
    }
}

public interface IDamageable
{
    void TakeDamage(in DamageInfo info);
}
```

```csharp
public class Health : MonoBehaviour, IDamageable
{
    [SerializeField, Min(1)] private int max = 100;

    public int Max => max;
    public int Current { get; private set; }
    public bool IsDead => Current <= 0;

    public event Action<int> Changed;    // passes the new value
    public event Action Died;

    private void Awake() => Current = max;

    public void TakeDamage(in DamageInfo info)
    {
        if (info.Amount <= 0 || IsDead) return;

        Current = Mathf.Max(0, Current - info.Amount);
        Changed?.Invoke(Current);
        if (IsDead) Died?.Invoke();
    }

    public void Heal(int amount)
    {
        if (amount <= 0 || IsDead) return;

        Current = Mathf.Min(max, Current + amount);
        Changed?.Invoke(Current);
    }
}
```

چرا این‌طور ساخته شده: `Health` هیچ چیزی از UI، صدا یا افکت‌ها نمی‌داند (آن‌ها خودشان به رویدادها سابسکرایب می‌کنند)؛ ورودی بی‌اعتبار نادیده گرفته می‌شود؛ شیء مرده را نمی‌شود درمان کرد؛ و `DamageInfo` می‌تواند بدون اینکه امضای متد عوض شود بزرگ‌تر شود (نوع آسیب، منبع و...).

## 22.2 کول‌داون

یک کلاس سادهٔ C# بدون هیچ وابستگی‌ای به یونیتی، پس تست‌کردنش هم آب خوردن است (فصل ۲۰).

```csharp
public class Cooldown
{
    private readonly float duration;
    private float remaining;

    public Cooldown(float duration) => this.duration = duration;

    public bool Ready => remaining <= 0f;
    public float Normalized =>
        duration <= 0f ? 1f : 1f - remaining / duration;

    public void Tick(float deltaTime)
        => remaining = Mathf.Max(0f, remaining - deltaTime);

    public bool TryUse()
    {
        if (!Ready) return false;
        remaining = duration;
        return true;
    }
}
```

```csharp
private readonly Cooldown fireCooldown = new Cooldown(0.25f);

private void Update()
{
    fireCooldown.Tick(Time.deltaTime);
    if (Input.GetButton("Fire1") && fireCooldown.TryUse()) Fire();
}
```

## 22.3 یک ماشین حالت قابل استفادهٔ مجدد

```csharp
public interface IState
{
    void Enter();
    void Tick();
    void Exit();
}

public class StateMachine
{
    public IState Current { get; private set; }

    public void ChangeState(IState next)
    {
        if (next == Current) return;
        Current?.Exit();
        Current = next;
        Current?.Enter();
    }

    public void Tick() => Current?.Tick();
}
```

```csharp یک state که هر چه لازم دارد را از سازندهٔ خودش می‌گیرد
public class ChaseState : IState
{
    private readonly Transform self;
    private readonly Transform target;
    private readonly float speed;

    public ChaseState(Transform self, Transform target, float speed)
    {
        this.self = self;
        this.target = target;
        this.speed = speed;
    }

    public void Enter() { }
    public void Exit() { }

    public void Tick()
    {
        self.position = Vector3.MoveTowards(
            self.position, target.position, speed * Time.deltaTime);
    }
}
```

هر state را یک‌بار (در `Awake`) بساز، در فیلدها نگهشان دار و از `Update` متد `machine.Tick()` را صدا بزن.

## 22.5 یک event bus ساده و تایپ‌دار

می‌گذارد سیستم‌های بی‌ربط از طریق نوع پیام با هم حرف بزنند، بدون هیچ ارجاع مستقیمی به هم.

```csharp
public static class EventBus<T> where T : struct
{
    private static event Action<T> Raised;

    public static void Subscribe(Action<T> handler) => Raised += handler;
    public static void Unsubscribe(Action<T> handler) => Raised -= handler;
    public static void Publish(T message) => Raised?.Invoke(message);

    [RuntimeInitializeOnLoadMethod(
        RuntimeInitializeLoadType.SubsystemRegistration)]
    private static void Reset() => Raised = null;
}

public readonly struct EnemyKilled
{
    public readonly int Points;
    public EnemyKilled(int points) => Points = points;
}

// Publish:    EventBus<EnemyKilled>.Publish(new EnemyKilled(50));
// Subscribe:  EventBus<EnemyKilled>.Subscribe(OnEnemyKilled);
```

> [warn] event bus جریان کد را قایم می‌کند
> سیستم‌ها را از هم جدا می‌کند، ولی دیگر سخت‌تر می‌بینی کی به چه چیزی واکنش می‌دهد. برای رویدادهای کلی بازی ازش استفاده کن؛ بین اشیای نزدیک به هم از رویدادهای مستقیم C# استفاده کن. رویدادهای static دلیل مهم‌بودن `Reset` هستند و دلیل اینکه هر `Subscribe` به یک `Unsubscribe` متناظر نیاز دارد.

## 22.6 اینونتوری

```csharp
public class Inventory
{
    private readonly Dictionary<int, int> counts = new();   // itemId to count

    public event Action<int, int> Changed;   // itemId, new count

    public int GetCount(int itemId)
        => counts.TryGetValue(itemId, out int c) ? c : 0;

    public void Add(int itemId, int amount = 1)
    {
        if (amount <= 0) return;
        int total = GetCount(itemId) + amount;
        counts[itemId] = total;
        Changed?.Invoke(itemId, total);
    }

    public bool TryRemove(int itemId, int amount = 1)
    {
        int have = GetCount(itemId);
        if (amount <= 0 || have < amount) return false;

        int left = have - amount;
        if (left == 0) counts.Remove(itemId);
        else counts[itemId] = left;
        Changed?.Invoke(itemId, left);
        return true;
    }
}
```

آیتم‌ها با شناسه (ID) شناخته می‌شوند تا اینونتوری ساده ذخیره و بارگذاری شود (فصل ۱۵)؛ جزئیات هر آیتم (نام، آیکون، محدودیت تعداد) داخل ScriptableObjectها می‌ماند (فصل ۱۲).

> [recap] جمع‌بندی فصل ۲۲
> - `Health`، کول‌داون، امتیاز و اینونتوری کلاس‌های ساده و تست‌پذیری هستند که خروجی‌شان را با رویداد اعلام می‌کنند.
> - ورودی را اعتبارسنجی کن، کارهای ناممکن را نادیده بگیر و رویداد را فقط وقتی چیزی واقعاً عوض شده بالا بیاور.
> - stateها و استراتژی‌ها را یک‌بار بساز؛ وابستگی‌ها را از راه سازنده سیم‌کشی کن.
> - وضعیت رویدادهای static را ریست کن و همیشه `Subscribe` را با یک `Unsubscribe` جفت کن.

# 23. پرسش و پاسخ مصاحبه

تمرین کن این‌ها را **بلند بلند** جواب بدهی. یک جواب خوب از یک الگو پیروی می‌کند: یک تعریف کوتاه و دقیق؛ یک مثال عینی از یونیتی؛ هزینه و فایده‌اش؛ اگر مهم بود تأثیرش روی کارایی یا حافظه؛ و اینکه کِی ازش استفاده نمی‌کنی.

## 23.1 مبانی

**س:** فرق کلاس و struct چیست؟
**ج:** کلاس یک نوع ارجاعی است: متغیرها یک ارجاع نگه می‌دارند و خودِ شیء روی heap زندگی می‌کند. struct یک نوع مقداری است و موقع انتساب کپی می‌شود. برای اشیایی که هویت و رفتار دارند از کلاس استفاده کن؛ برای دادهٔ مقدار‌مانند مثل `DamageInfo` یک struct کوچک و ترجیحاً immutable بگذار. structهایی که قابل تغییرند باعث باگ‌های کپی می‌شوند.

**س:** هر struct روی stack است؟
**ج:** نه. یک struct که داخل یک کلاس، یک آرایه یا یک closure باشد، به‌عنوان بخشی از همان شیء روی heap زندگی می‌کند.

**س:** بوکسینگ (boxing) چیست؟
**ج:** تبدیل یک نوع مقداری به `object` یا یک اینترفیس، که یک شیء روی heap تخصیص می‌دهد. اگر زیاد تکرارش کنی زباله (garbage) تولید می‌کند؛ مثلاً پاس‌دادن intها به پارامترهای `object` در `Update`.

**س:** فرق `const` و `readonly` چیست؟
**ج:** `const` یک ثابت زمان کامپایل است که داخل خودِ کدی که ازش استفاده می‌کند پخته می‌شود. `readonly` یک‌بار در زمان اجرا مقدار می‌گیرد، همان‌جا در تعریف یا در سازنده. برای مقدارهایی که ممکن است بین نسخه‌ها عوض شوند `static readonly` بگذار.

**س:** `var` چه کار می‌کند؟
**ج:** کامپایلر نوع را در زمان کامپایل استنتاج می‌کند. همچنان استاتیک‌تایپ است و با `dynamic` فرق دارد.

**س:** `ref`، `out` و `in` چیستند؟
**ج:** `ref` یک متغیر را با ارجاع پاس می‌دهد، هم برای خواندن و هم برای نوشتن. `out` متد را مجبور می‌کند مقدارش را حتماً تعیین کند (در الگوی `Try` به کار می‌آید). `in` هم با ارجاع پاس می‌دهد ولی فقط‌خواندنی، که جلوی کپی‌شدن structهای بزرگ را می‌گیرد.

**س:** جمع‌آوری زباله (garbage collection) چیست؟
**ج:** آزادسازی خودکار اشیای managed‌ی که دیگر چیزی به آن‌ها ارجاع نمی‌دهد. هزینه‌اش زمان CPU است و می‌تواند باعث پرش فریم شود؛ برای همین بازی‌ها تخصیص حافظه در کدهایی که زیاد اجرا می‌شوند را تا جای ممکن کم می‌کنند.

## 23.2 شیءگرایی و طراحی

**س:** چندریختی (polymorphism) چیست؟
**ج:** کد با یک نوع پایه یا یک اینترفیس کار می‌کند و نوع واقعی رفتار را در زمان اجرا تأمین می‌کند. زنجیره‌های `if` برای چک‌کردن نوع را حذف می‌کند و می‌گذارد بدون دست‌زدن به کد موجود، گونه‌های جدید اضافه کنی.

**س:** اینترفیس یا کلاس abstract؟
**ج:** اینترفیس برای یک قابلیت مشترک بین نوع‌های بی‌ربط (`IDamageable`). کلاس abstract برای خانواده‌ای از نوع‌های مرتبط که وضعیت و کد مشترک دارند (`EnemyBase`). یک کلاس می‌تواند چند اینترفیس پیاده کند ولی فقط از یک کلاس ارث می‌برد.

**س:** «composition به‌جای ارث‌بری» یعنی چه؟
**ج:** اشیاء را از کامپوننت‌های کوچک بساز، نه از سلسله‌مراتب عمیق کلاس‌ها. مدل GameObject/Component که خود یونیتی دارد همان composition است. این‌طوری برای هر ترکیب رفتار لازم نیست یک زیرکلاس تازه بسازی.

**س:** اصول SOLID کدام‌اند؟
**ج:** تک‌مسئولیتی (SRP)، باز/بسته (OCP)، جانشینی لیسکوف (LSP)، تفکیک اینترفیس (ISP) و وارونگی وابستگی (DIP). هدفشان با هم این است که کد را راحت بتوانی گسترش بدهی و تست کنی. من عمل‌گرایانه ازشان استفاده می‌کنم و تا نیاز واقعی نباشد سراغ انتزاع اضافه نمی‌روم.

**س:** مشکل Singletonها چیست؟
**ج:** وابستگی‌های قایم، تست‌پذیری ضعیف، دردسرهای چرخهٔ عمر و ترتیب مقداردهی، و این تمایل که آخرش به یک God object تبدیل شود. برای سرویس‌های ساده و واقعاً یکتا اشکالی ندارد، ترجیحاً پشت یک اینترفیس.

**س:** الگوی State یا الگوی Strategy؟
**ج:** Strategy الگوریتم‌های قابل‌تعویض را از بیرون عوض می‌کند. State رفتار را بر اساس وضعیت داخلی و همراه با گذارها تغییر می‌دهد. ساختارشان شبیه است؛ ولی نیتشان فرق دارد.

**س:** تزریق وابستگی یا Service Locator؟
**ج:** DI وابستگی‌ها را صریح می‌کند و در تست‌ها راحت می‌توانی جعلشان کنی. Service locator سریع راه می‌افتد ولی وابستگی‌ها را قایم می‌کند. من DI را ترجیح می‌دهم و در پروژه‌های کوچک locator را هم قابل‌قبول می‌دانم.

## 23.3 قابلیت‌های C#

**س:** رویدادها با delegate چه فرقی دارند؟
**ج:** یک `event` دور یک delegate لفافه می‌پیچد تا کد بیرونی فقط بتواند سابسکرایب و آن‌سابسکرایب کند، نه اینکه صدایش بزند یا هندلرهایش را عوض کند. پیاده‌سازی الگوی Observer در خودِ زبان است.

**س:** خطر رویدادها چیست؟
**ج:** فراموش‌کردن آن‌سابسکرایب باعث می‌شود سابسکرایبر همچنان قابل‌دسترس بماند و ممکن است روی اشیای نابودشده صدا زده شود. من در `OnEnable` سابسکرایب می‌کنم و در `OnDisable` آن‌سابسکرایب.

**س:** `event` سی‌شارپ یا `UnityEvent`؟
**ج:** رویدادهای C# برای ارتباط کد-به-کد: ایمن‌به‌نوع و سریع. `UnityEvent` وقتی طراح‌ها باید رفتار را از داخل Inspector سیم‌کشی کنند.

**س:** کِی از LINQ پرهیز می‌کنی؟
**ج:** در کدهایی که هر فریم اجرا می‌شوند و بقیهٔ مسیرهای پرتکرار، چون enumerator و closure تخصیص می‌دهد. برای راه‌اندازی، ابزارها و کدهای کم‌تکرار هیچ ایرادی ندارد. قبل از تصمیم‌گرفتن پروفایل می‌گیرم.

**س:** `?.` و `??` چه کار می‌کنند و تله‌شان در یونیتی چیست؟
**ج:** `?.` اگر سمت چپش null باشد ادامه نمی‌دهد؛ `??` یک مقدار جایگزین می‌دهد. یونیتی برای `UnityEngine.Object` عملگر `==` را بازتعریف کرده، پس اشیای نابودشده با null برابر حساب می‌شوند، ولی `?.` و `??` این بازتعریف را دور می‌زنند. برای اشیای یونیتی از `== null` یا `if (obj)` استفاده کن.

**س:** چرا جنریک‌ها از `object` بهترند؟
**ج:** ایمنی نوع در زمان کامپایل، بدون cast، بدون بوکسینگ نوع‌های مقداری، و کدی که می‌شود دوباره به کارش برد.

**س:** Dictionary یا List؟
**ج:** Dictionary وقتی کار اصلی جست‌وجو با کلید است (به‌طور میانگین O(1)). List وقتی ترتیب و پیمایش مهم است. HashSet وقتی فقط یکتایی و عضویت را لازم داری.

**س:** closure چیست و چرا برای کارایی مهم است؟
**ج:** یک لامبدا که متغیرهایی از اسکوپ اطرافش را در خودش capture می‌کند. کامپایلر یک شیء قایم برای نگه‌داشتن آن‌ها می‌سازد که تخصیص حافظه دارد. در مسیرهای پرتکرار از لامبدای static یا متد نام‌دار استفاده کن.

## 23.4 جزئیات یونیتی

**س:** ترتیب اجرای Awake، OnEnable و Start چیست؟
**ج:** اول `Awake`، بعد `OnEnable`، بعد `Start` پیش از اولین `Update`. `Awake` و `OnEnable` همهٔ اشیاء قبل از هر `Start`ای اجرا می‌شوند. ترتیب بین اسکریپت‌های مختلف تعریف‌نشده است، مگر اینکه خودت صریح تعیینش کنی.

**س:** Update، FixedUpdate و LateUpdate؟
**ج:** `Update` هر فریم برای منطق و ورودی اجرا می‌شود. `FixedUpdate` با گام زمانی ثابت برای فیزیک اجرا می‌شود. `LateUpdate` بعد از همهٔ `Update`ها اجرا می‌شود؛ مثلاً برای دوربینی که بازیکن را دنبال می‌کند.

**س:** کوروتین یا async/await؟
**ج:** کوروتین برای توالی‌های فریم‌به‌فریم و زمان‌بندی وابسته به یک GameObject. `async/await` برای ورودی/خروجی، درخواست‌های شبکه و ترکیب کارهای ناهمگام، همراه با cancellation token.

**س:** کوروتین یک ترد (thread) است؟
**ج:** نه. روی ترد اصلی اجرا می‌شود و در هر `yield` ادامه پیدا می‌کند.

**س:** می‌شود از داخل یک Task سراغ APIهای یونیتی رفت؟
**ج:** فقط روی ترد اصلی. وقتی روی ترد اصلی `await` می‌کنی، ادامه‌اش هم به همان ترد برمی‌گردد، ولی کدی که داخل `Task.Run` است نباید از اشیای یونیتی استفاده کند.

**س:** چرا از ScriptableObject استفاده می‌کنیم؟
**ج:** دادهٔ مشترک و دارایی‌پایه که طراح‌ها بدون کد می‌توانند ویرایشش کنند؛ این‌طوری یک منبع حقیقت واحد داری و تکرار کم می‌شود. وضعیت زمان اجرا نباید داخلشان باشد، چون تغییرهایی که در ادیتور می‌دهی باقی می‌مانند.

**س:** یونیتی چه چیزهایی را سریالایز می‌کند؟
**ج:** فیلدهای public و `[SerializeField]` از نوع‌های پشتیبانی‌شده. نه پراپرتی‌ها، نه دیکشنری‌ها، نه فیلدهای static، نه اینترفیس‌ها و نه مقدارهای چندریختی بدون `[SerializeReference]`.

**س:** چرا `GetComponent` داخل `Update` دردسر است؟
**ج:** چون هر فریم جست‌وجو را از نو تکرار می‌کند. نتیجه را در `Awake` کش کن. این کار به‌طور کلی ممنوع نیست، ولی هر چیزی را که مکرر می‌خوانی کش کن.

## 23.5 کارایی و حافظه

**س:** چطور یک مشکل کارایی را پیدا می‌کنی؟
**ج:** یک بیلد توسعه روی دستگاه هدف پروفایل می‌کنم، فریم‌ها و متدهای گران را پیدا می‌کنم، GC Alloc را چک می‌کنم، بزرگ‌ترین هزینه را درست می‌کنم و دوباره اندازه می‌گیرم.

**س:** چه چیزهایی در یونیتی زباله (garbage) تولید می‌کنند؟
**ج:** ساختن مجموعه‌ها و اشیای تازه در هر فریم، کار با رشته‌ها، بوکسینگ، لامبداهایی که چیزی را capture می‌کنند، LINQ، `foreach` روی اینترفیس‌ها، و APIهایی که آرایهٔ جدید برمی‌گردانند.

**س:** کِی از object pool استفاده می‌کنی؟
**ج:** برای اشیایی که زیاد ساخته و نابود می‌شوند، آن هم وقتی پروفایل نشان می‌دهد `Instantiate`، `Destroy` یا GC واقعاً هزینه دارند. موقع استفادهٔ دوباره وضعیت را ریست کن و هر شیء را دقیقاً یک‌بار آزاد کن.

**س:** چطور یک نشتی حافظه (memory leak) را پیدا می‌کنی؟
**ج:** اسنپ‌شات‌های Memory Profiler را قبل و بعد از یک چرخهٔ کامل مقایسه می‌کنم، بعد دنبال این می‌گردم که چه چیزی ارجاع را نگه داشته: فیلدهای static، سابسکرایب‌های رویداد، کش‌ها یا هندل‌های آزاد‌نشده.

**س:** با وجود GC چرا هنوز به `IDisposable` نیاز داریم؟
**ج:** GC حافظهٔ managed را آزاد می‌کند ولی منابع unmanaged مثل فایل‌ها، streamها و کانتینرهای native را نه. این‌ها به آزادسازی قطعی با `using` یا `Dispose` نیاز دارند.

## 23.6 پرسش‌های سناریویی

**س:** بازی هر چند ثانیه یک‌بار تیک می‌زند. چه کار می‌کنی؟
**ج:** یک بیلد توسعه را پروفایل می‌کنم. یک فریم پرش‌دار را با یک فریم عادی مقایسه می‌کنم. روی تایم‌لاین CPU و GC Alloc نگاه می‌کنم و دنبال تخصیص‌ها، `Instantiate`، LINQ، ساختن رشته یا بارگذاری می‌گردم. علت را درست می‌کنم و بعد با یک اسنپ‌شات جدید تأیید می‌گیرم.

**س:** `Health` باید به UI، صدا و افکت‌ها خبر بدهد. چطور طراحی‌اش می‌کنی؟
**ج:** `Health` رویداد بالا می‌آورد (`Changed`، `Died`). UI، صدا و VFX به همان‌ها سابسکرایب می‌کنند. `Health` هیچ ارجاعی به آن سیستم‌ها ندارد، پس اضافه‌کردن یک واکنش جدید هیچ‌وقت `Health` را دست نمی‌زند.

**س:** پنج نوع هوش مصنوعی دشمن داری و کد `if/else` از کنترل خارج شده.
**ج:** برای الگوریتم‌های قابل‌تعویض حرکت یا حمله یک استراتژی می‌گذارم، و وقتی رفتار به وضعیت با گذارهای مشخص وابسته است یک ماشین حالت. داده‌ای مثل سرعت‌ها و بردها هم می‌رود در ScriptableObjectها.

**س:** اسکین‌های تزئینی باید فقط وقتی لازم شد دانلود شوند.
**ج:** Addressables با یک گروه ریموت. اندازهٔ دانلود را چک می‌کنم، `DownloadDependenciesAsync` را صدا می‌زنم، بارگذاری و instantiate می‌کنم و وقتی اسکین دیگر استفاده نمی‌شود هندل را آزاد می‌کنم.

**س:** یک سیستم ذخیره را چطور ساختاردهی می‌کنی؟
**ج:** کلاس‌های دادهٔ سریالایزشده با شمارهٔ نسخه، یک سرویس ذخیره پشت یک اینترفیس، نوشتن در فایل موقت همراه با یک نسخهٔ پشتیبان، شناسه به‌جای ارجاع به شیء، اعتبارسنجی و مهاجرت موقع بارگذاری، و برای هر چیز رقابتی مدلی که سرور حرف آخر را بزند.

> [interview] فرمول جواب‌دادن
> 1. یک تعریف کوتاه و دقیق. 2. یک مثال واقعی از یونیتی. 3. هزینه و فایده‌اش. 4. تأثیرش روی کارایی یا حافظه، اگر مهم بود. 5. در معماری: وابستگی بین بخش‌ها و تست‌پذیری. 6. کِی ازش استفاده **نمی‌کنی**. اگر چیزی را نمی‌دانی، بگو نمی‌دانم و توضیح بده چطور می‌خواهی پیدایش کنی.

# 24. پروژهٔ پایانی

ساختن یک بازی کوچک که بیشتر این کتاب را به کار می‌گیرد، دانش را تبدیل به مهارت می‌کند. یک شوتر از نمای بالا یا از نمای کنار انتخاب کن. گرافیک را ساده نگه دار؛ هدف خودِ کد است.

## 24.1 نیازمندی‌ها

1. **Player** با `Health`، حرکت و یک سلاح.
2. **دشمن‌ها** با `Health` و استراتژی‌های AI قابل‌تعویض (تعقیب، فرار، گشت).
3. رویدادهای Health رابط کاربری را می‌چرخانند؛ نوار جان هیچ‌وقت `Health` را داخل `Update` نمی‌خواند.
4. **سلاح‌ها** با یک اینترفیس یا کلاس پایهٔ abstract طراحی شوند (`IWeapon`).
5. **گلوله‌ها** با یک object pool مدیریت شوند.
6. **`WeaponData` و `EnemyData`** به‌صورت ScriptableObject.
7. **وضعیت‌های بازی** (Menu، Playing، Paused، GameOver) با یک ماشین حالت.
8. **امتیاز** با رویداد به UI و یک سرویس آنالیتیکس اعلام شود.
9. یک **سرویس آنالیتیکس جعلی** که با تزریق وابستگی داده می‌شود.
10. **ذخیره و بارگذاری** دادهٔ بازیکن به‌صورت JSON با شمارهٔ نسخه و نسخهٔ پشتیبان.
11. یک **درخواست جعلی به سرور** با `async/await` و قابلیت کنسل‌شدن.
12. **پروفایل** بازی و حذف بزرگ‌ترین تخصیص‌های حافظه.

## 24.2 ساختار پیشنهادی

```text
Scripts/
  Core/       GameBootstrap, GameStateMachine, ServiceLocator
  Player/     PlayerController, PlayerWeapon
  Enemies/    EnemyController, IMoveStrategy, ChaseStrategy
  Combat/     IDamageable, DamageInfo, Health, BulletPool, Bullet
  Data/       WeaponData, EnemyData, SaveData
  Services/   IAnalyticsService, FakeAnalyticsService, SaveSystem
  UI/         HealthPresenter, HealthView, ScoreView
Tests/
  EditMode/   CooldownTests, InventoryTests, SaveDataTests
```

## 24.3 ترتیب ساخت

1. حرکت و شلیک با یک `Instantiate` موقت.
2. `Health`، `IDamageable`، آسیب و مرگ.
3. جای `Instantiate` را با object pool عوض کن.
4. عددهای سلاح و دشمن را ببر در ScriptableObjectها.
5. استراتژی‌های دشمن را اضافه کن، بعد ماشین حالت بازی را.
6. UI از راه رویدادها؛ امتیاز و آنالیتیکس.
7. ذخیره و بارگذاری؛ درخواست جعلی به سرور.
8. برای کلاس‌های سادهٔ C# تست Edit Mode بنویس.
9. پروفایل بگیر، درست کن و عددهای قبل و بعد را یادداشت کن.

## 24.4 خودت را امتحان کن

- می‌توانی هر کلاس را در یک جمله و بدون استفاده از کلمهٔ «و» توضیح بدهی؟
- اگر UI را پاک کنی، گیم‌پلی همچنان کامپایل و اجرا می‌شود؟
- همهٔ سابسکرایب‌های رویداد جفتشان هست، و Memory Profiler بعد از یک‌بار دیگر بازی‌کردن یک مرحله هیچ رشدی نشان نمی‌دهد؟
- پروفایلر در حین بازی معمولی صفر تخصیص GC در هر فریم نشان می‌دهد؟
- می‌توانی پیاده‌سازی آنالیتیکس را با عوض‌کردن یک خط عوض کنی؟

**کارهای سخت‌تر برای بعد:** Addressables برای پریفب دشمن‌ها، یک ادیتور مرحله با قابلیت undo به کمک الگوی Command، یک راه‌اندازی VContainer، و جمعیتی هزارتایی از ایجنت‌ها با Job System.

# 25. مرجع سریع

برگه‌های تقلب برای مرور سریع. اگر خطی این‌جا برایت ناآشناست، برگرد به فصل مربوطه.

## 25.1 مفاهیم در یک نگاه

| مفهوم | خلاصه در یک خط |
|---|---|
| class | نوع ارجاعی، هویت و رفتار |
| struct | نوع مقداری، دادهٔ کوچک مقدار‌مانند (ترجیحاً `readonly`) |
| interface | قرارداد قابلیت‌ها؛ چند تا در هر کلاس |
| abstract class | پایهٔ مشترک با وضعیت و کد؛ فقط یکی در هر کلاس |
| generic | قابل استفادهٔ مجدد و ایمن‌به‌نوع؛ بدون بوکسینگ |
| delegate | ارجاع به کدی که می‌شود صدایش زد |
| event | delegate با دسترسی محدود: فقط سابسکرایب و آن‌سابسکرایب |
| LINQ | کوئری‌های خواناتر؛ نه برای مسیرهای پرتکرار |
| exception | خطای غیرمنتظره؛ نه مسیر عادی اجرا |
| `async` / `await` | انتظارهای بدون بلاک‌کردن؛ cancellation token پاس بده |
| coroutine | توالی روی ترد اصلی، وابسته به یک GameObject |
| ScriptableObject | دارایی دادهٔ مشترک؛ بدون وضعیت زمان اجرای قابل‌تغییر |
| IDisposable | آزادسازی قطعی منابع unmanaged |

## 25.2 بکن و نکن

| بکن | نکن |
|---|---|
| فیلدهای `[SerializeField] private` | فیلدهای public فقط برای راحتی Inspector |
| کش‌کردن ارجاع‌ها در `Awake` | `GetComponent` یا `Find` داخل `Update` |
| سابسکرایب در `OnEnable`، آن‌سابسکرایب در `OnDisable` | رها کردن رویدادهای سابسکرایب‌شده |
| `TryGetValue`، `TryGetComponent`، `CompareTag` | دو بار جست‌وجو، مقایسهٔ رشته‌ای تگ |
| استفادهٔ دوباره و `Clear()` روی مجموعه‌ها | `new List<T>()` در هر فریم |
| پاس‌دادن `CancellationToken` به کار ناهمگام | تسک‌های fire-and-forget بدون مدیریت خطا |
| `== null` برای اشیای یونیتی | `?.`، `??`، `is null` روی اشیای یونیتی |
| `InvariantCulture` برای عددهای ذخیره‌شده | کالچر پیش‌فرض برای فایل ذخیره |
| پروفایل‌گرفتن از بیلد روی دستگاه | بهینه‌سازی بر اساس حدس |
| نگه‌داشتن منطق در کلاس‌های سادهٔ C# | گذاشتن همه‌چیز در یک MonoBehaviour |

## 25.3 ترتیب چرخهٔ عمر

| ترتیب | متد |
|---|---|
| 1 | `Awake` |
| 2 | `OnEnable` |
| 3 | `Start` |
| 4 | `FixedUpdate` (صفر بار یا بیشتر در هر فریم) |
| 5 | `Update` |
| 6 | `LateUpdate` |
| 7 | `OnDisable` |
| 8 | `OnDestroy` |

## 25.4 برگهٔ تقلب مجموعه‌ها

| لازم داری | استفاده کن |
|---|---|
| یک لیست پویا | `List<T>` |
| اندازهٔ ثابت، سریع‌ترین | `T[]` |
| جست‌وجو با کلید | `Dictionary<K,V>` همراه با `TryGetValue` |
| آیتم‌های یکتا یا چک‌کردن عضویت | `HashSet<T>` |
| اولین ورودی، اولین خروجی | `Queue<T>` |
| آخرین ورودی، اولین خروجی | `Stack<T>` |
| افشای امن به بیرون | `IReadOnlyList<T>` |

## 25.5 چک‌لیست قبل از کامیت

1. هیچ هشدار کامپایلری‌ای که نفهمی نداری.
2. هیچ `Debug.Log` اضافه‌ای در مسیرهای پرتکرار جا نمانده.
3. هر `+=` یک `-=` متناظر دارد.
4. داخل `Update` هیچ `Find`، `GetComponent` یا LINQ نداری.
5. ارجاع‌های سریالایزشده پر شده‌اند (یا در `OnValidate` اعتبارسنجی می‌شوند).
6. نام فایل‌ها همان نام کلاس‌هاست؛ namespaceها با پوشه‌ها یکی‌اند.
7. در هر فریم چیز بزرگی تخصیص نمی‌شود (در Profiler چکش کرده‌ای).
8. فایل‌های `.meta` کامیت شده‌اند؛ پوشهٔ `Library` یا `Temp` نداری.
9. منطق جدید اگر C# ساده است، حداقل یک تست دارد.
10. می‌توانی این تغییر را در یک جمله توضیح بدهی.

## 25.6 واژه‌نامه

| اصطلاح | معنی |
|---|---|
| Allocation | رزرو حافظهٔ heap برای یک شیء تازه |
| AOT / IL2CPP | کامپایل از پیش C# به کد native |
| Assembly definition | فایل یونیتی‌ای که یک اسمبلی کد جدا تعریف می‌کند |
| Boxing | پیچیدن یک نوع مقداری داخل یک شیء روی heap |
| Closure | یک لامبدا به‌همراه متغیرهایی که capture کرده |
| Coupling | شدت وابستگی یک تکه کد به تکهٔ دیگر |
| Hot path | کدی که خیلی زیاد اجرا می‌شود، مثل هر فریم |
| Main thread | تردی که استفاده از APIهای یونیتی فقط در آن مجاز است |
| Prefab | یک قالب GameObject قابل استفادهٔ مجدد |
| Serialization | تبدیل داده به شکلی قابل ذخیره و برگرداندنش |
| Stripping | حذف کدهایی که در زمان بیلد بی‌استفاده به نظر می‌رسند |

## 25.7 از این‌جا کجا بروم

- **مستندات رسمی:** راهنمای یونیتی و Scripting API برای همان نسخه‌ای که داری، و مستندات زبان C# مایکروسافت.
- **کتاب‌ها و راهنماهای رایگان:** *Game Programming Patterns* نوشتهٔ Robert Nystrom (آنلاین و رایگان)، *Clean Code* نوشتهٔ Robert C. Martin، و کتاب‌های رایگان خودِ یونیتی دربارهٔ سبک کد، الگوهای برنامه‌نویسی بازی و بهینه‌سازی کارایی.
- **ابزارهایی که بعداً یاد بگیر:** Unity Profiler و Memory Profiler، Unity Test Framework، Addressables، و بعدها Job System همراه با Burst.
- **تمرین:** پروژهٔ پایانی را در یک ژانر دیگر از نو بساز و پروژه‌های اوپن‌سورس یونیتی بقیه را بخوان.

> [recap] این را یادت باشد
> C# را یاد بگیر تا سیستم واقعی بسازی، نه برای حفظ‌کردن. اول کارش بینداز، بعد شفافش کن، بعد سریعش کن — و قبل از بهینه‌سازی اندازه بگیر.
